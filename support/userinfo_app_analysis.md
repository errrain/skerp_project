# userinfo 앱 분석 보고서

## 1) 개요
- `userinfo` 앱은 프로젝트의 커스텀 사용자 모델(`CustomUser`)과 사용자 CRUD 화면을 담당합니다.
- Django 기본 `AbstractUser`를 확장하고, `AUTH_USER_MODEL = "userinfo.CustomUser"`로 전역 사용자 모델로 사용됩니다.
- 특히 `is_internal`(사내/외부 구분)과 `vendor`(거래처 연결) 필드를 통해 협력사 사용자 범위를 통제하는 기반을 제공합니다.

## 2) 현재 구조 요약

### 2.1 모델
- `CustomUser`는 `full_name`, `department`, `level`, `status`, `phone`, `email`, `is_internal`, `vendor`를 가집니다.
- `email`은 유니크 제약이 있으며, 외부 사용자 식별 및 알림 채널로도 활용 가능한 구조입니다.
- `vendor`는 `SET_NULL` FK로 설계되어 거래처 삭제 시 사용자 계정은 보존됩니다.

### 2.2 폼
- `CustomUserForm`는 생성/수정 공용 폼입니다.
- `clean()`에서 비즈니스 룰을 구현:
  - 외부 사용자(`is_internal=False`)는 `vendor` 필수
  - 사내 사용자(`is_internal=True`)는 `vendor`를 `None`으로 정규화
- `vendor` 선택지는 `can_login=True`, `status='active'` 거래처로 제한되어 있어 데이터 품질 측면의 장점이 있습니다.

### 2.3 뷰/URL
- 리스트/생성/수정/삭제의 기본 CRUD를 함수형 뷰로 제공합니다.
- 비밀번호는 생성/수정 시 `set_password()`를 호출해 해시 저장 처리합니다.
- URL은 `/userinfo/` 하위로 구성되어 있으며 라우팅 명명은 명확합니다.

### 2.4 템플릿
- 리스트 화면은 기본 사용자 속성 조회 중심입니다.
- 폼 화면에서 `is_internal` 체크에 따라 `vendor` 활성/비활성을 JS로 제어합니다.

## 3) 잘 되어 있는 점 (강점)
1. **커스텀 유저 모델 선적용**
   - 프로젝트 초기에 `AUTH_USER_MODEL`을 커스텀으로 고정한 점은 장기 유지보수에 유리합니다.
2. **협력사 스코프의 데이터 기반 마련**
   - `is_internal + vendor` 조합은 다른 앱(예: 협력사 발주 화면)의 권한 분기와 잘 맞물립니다.
3. **비밀번호 해시 저장 처리**
   - 생성/수정 뷰에서 `set_password()`를 사용하고 있어 평문 저장 리스크를 회피합니다.
4. **폼 레벨 비즈니스 룰 적용**
   - 외부 사용자의 거래처 강제 지정 규칙이 폼 검증으로 명시되어 있습니다.

## 4) 주요 리스크 및 개선 필요사항

### 4.1 접근 제어(가장 우선)
- 현재 userinfo 뷰에는 `@login_required`, 권한 체크(`staff/superuser/권한코드`)가 없습니다.
- 결과적으로 URL을 아는 사용자가 사용자 목록 조회/생성/수정/삭제에 접근할 가능성이 있습니다.
- **권장**: 최소 `@login_required` + 관리자 권한 데코레이터(`user_passes_test` 혹은 `PermissionRequiredMixin`) 적용.

### 4.2 삭제 방식
- `user_delete`는 하드 삭제(`delete()`)를 수행합니다.
- 사용자 계정은 감사/이력/참조 무결성을 위해 보통 `is_active=False` 비활성화가 권장됩니다.
- **권장**: 하드 삭제 대신 비활성화 플로우로 전환하고, 화면에서도 “삭제” 대신 “비활성화” 용어 사용.

### 4.3 생성/수정 폼 비밀번호 UX
- 현재 `password` 필드가 생성/수정 공용이며 수정 시 빈 값이면 변경 안 함 로직입니다.
- 기능상 동작하지만, 운영 관점에서 “초기 비밀번호 설정”과 “비밀번호 변경”을 분리하는 편이 오류를 줄입니다.
- **권장**: 생성 폼/수정 폼 분리 또는 Django 내장 `SetPasswordForm`/`PasswordChangeForm` 활용.

### 4.4 민감정보 로그 출력
- 뷰에서 `print()`로 POST 흐름/폼 오류를 출력합니다.
- 운영 환경에서 콘솔 로그가 누적될 경우 개인정보 또는 내부 검증 정보 노출 가능성이 있습니다.
- **권장**: `logging` 모듈로 전환, 민감 필드 마스킹, 로그 레벨 통제.

### 4.5 테스트 부재
- `userinfo/tests.py`는 실질 테스트가 없습니다.
- 핵심 비즈니스 룰(외부 사용자의 vendor 필수, 권한 제어, 비밀번호 해시 저장)은 회귀 테스트 대상입니다.
- **권장**: 모델/폼/뷰 테스트 최소 세트 구축.

### 4.6 템플릿/표시 정책
- 리스트 화면에 `is_internal`, `vendor` 컬럼이 표시되지 않아 운영자가 사용자 범주를 즉시 파악하기 어렵습니다.
- **권장**: 해당 컬럼 추가 및 필터(사내/외부, 거래처별) 제공.

## 5) 개선 로드맵 (우선순위)

### P0 (즉시)
1. `userinfo` 전 뷰 로그인/권한 데코레이터 적용
2. 삭제를 `is_active=False` 비활성화 방식으로 변경
3. `print()` 제거 및 표준 로깅 적용

### P1 (단기)
1. 비밀번호 정책/화면 분리(사용자정보 수정 vs 비밀번호 변경)
2. 목록 필터(사내/외부/거래처/상태) 추가
3. 사용자 생성 시 기본 상태(`pending`) 기반 승인 플로우 명확화

### P2 (중기)
1. 역할(Role) 체계 고도화 (`level` 문자열 대신 그룹/권한 중심)
2. 사용자 감사로그(누가 언제 생성/수정/상태변경했는지) 도입
3. SSO/사내 계정 연동 가능성 검토

## 6) 테스트 권장 항목
- 폼 검증
  - 외부 사용자 + vendor 없음 => invalid
  - 사내 사용자 + vendor 있음 => 저장 시 vendor null 처리
- 뷰 검증
  - 비로그인 접근 차단
  - 일반 사용자 접근 차단(관리자만 허용)
  - 생성/수정 시 비밀번호 해시 저장 확인
- 계정 상태
  - 비활성 사용자 로그인 불가
  - “삭제(비활성화)” 후 참조 데이터 무결성 유지

## 7) 결론
- `userinfo` 앱은 **커스텀 사용자 모델과 협력사 스코프 필드가 잘 갖춰진 기반**입니다.
- 다만, 운영 안정성 관점에서 **접근 제어/삭제 정책/테스트 부재**는 우선적으로 보완해야 합니다.
- 권한 통제와 계정 라이프사이클을 정교화하면, 다른 도메인 앱(협력사 발주/구매/품질)과의 보안 경계도 함께 강화될 수 있습니다.
